# Deploying the Fastify API to cPanel

Target hostname: **https://api.exoexpress.ma**

> **Status at the time of writing (2026-10-22): NOT DEPLOYED.**
>
> This document is an audit and deployment plan only. No production files were
> uploaded, no DNS or SSL settings were changed, no production environment
> variables were modified, and no production database was connected to or
> migrated. Local typechecks/tests used the existing local test database only.
>
> Read-only production probes on 2026-10-22:
>
> - `https://www.exoexpress.ma/` → `200`
> - `https://www.exoexpress.ma/dashboard/` → `404`
> - `https://api.exoexpress.ma/health` → `404`
> - `https://api.exoexpress.ma/health/ready` → `404`
>
> The public website is intact, but the API is not reachable at the expected
> health endpoints and the dashboard is not uploaded.

This runbook is separate from the static dashboard runbook in
[`DEPLOY_CPANEL.md`](./DEPLOY_CPANEL.md). The dashboard remains a static
Next.js export and is not affected by the API deployment.

## 1. Verdict

The API is **repo-side compatible** with a cPanel-style Node.js application
runner that:

- provides Node.js 20 or newer,
- runs a long-lived Node process,
- supplies a TCP `PORT`,
- can reach PostgreSQL, and
- can execute Prisma Client generation once during deployment.

However, **cPanel cannot be declared a viable host yet**. The gating items are
the hosting plan's Node.js version, its Node application runner, and especially
whether it provides a compatible PostgreSQL database. Those are provider/UI
facts, not repository facts, and must be confirmed before deployment.

Do not treat any item below as available until it has been checked in the
actual cPanel account or confirmed by the hosting provider.

## 2. Verified repository facts

| Fact | Evidence |
| --- | --- |
| API framework | Fastify `5.12.7` is installed from `apps/api/package-lock.json`; the repository requires Node.js 20+. |
| Runtime entrypoint | `apps/api/src/server.ts`, compiled to `apps/api/dist/server.js` by `tsc`. It uses ESM and top-level `await`. |
| Start command | Added `npm start` → `node dist/server.js`. Passenger can also use `dist/server.js` directly as the startup file. |
| Port handling | `config.port` uses `API_PORT` first, then the host-assigned `PORT`, then `3001`. On cPanel, do not override the assigned `PORT` unless the provider explicitly requires it. |
| Bind address | `HOST` defaults to `0.0.0.0`. `127.0.0.1` can be set if the runner requires loopback; this must be tested with the actual runner. |
| Workspace dependency | The API has **no runtime imports from `@exo/shared`** and no `workspace:*` dependencies. `apps/api` is self-contained and can be deployed without the monorepo root. |
| Database | Prisma `6.19.3` (from the lockfile), provider `postgresql`, datasource URL from `DATABASE_URL`. |
| Schema features | Enums, `JSONB`, `NUMERIC`, and `TIMESTAMP(3)` only. The migrations do not create PostgreSQL extensions and do not use `gen_random_uuid()`; IDs are generated by Prisma. |
| Migrations | `apps/api/prisma/migrations/20260101000000_init` and `20260102000000_courier_finance`. Production migrations must use `prisma migrate deploy`, never `migrate dev`, `db push`, reset, or seed. |
| Prisma engine | Prisma uses a native query engine binary. The local Windows install contains `query_engine-windows.dll.node`; a Linux/cPanel host must generate its own engine. Do not upload the local `node_modules` or `dist` as a Linux artifact. |
| Prisma generation | `prisma` and `tsx` are dev dependencies. The production sequence must install dev dependencies, run `prisma generate`, build, then prune dev dependencies. |
| Automatic schema changes | The server startup code does not call migrations, `db push`, seeds, resets, or destructive SQL. Only a read-only `SELECT 1` is used by `/health/ready`. |
| Redis | `ioredis` is declared but unused by the API. Redis is **not required** for this deployment. Sessions and rate-limit counters are database-backed/in-memory respectively. |
| Authentication transport | Bearer tokens in the `Authorization` header. The API does not set cookies and CORS uses `credentials: false`. Cookie `SameSite`/`Secure` settings therefore do not apply to the API. |
| Dashboard token storage | The dashboard stores the bearer token in browser `localStorage`. HTTPS and a sound static-site CSP/XSS posture are important; this is not a cPanel API setting. |
| CORS | Production CORS is now validated as exact HTTPS origins, with no wildcard, path, or trailing slash. Configure `CORS_ORIGINS=https://www.exoexpress.ma`. |
| Health endpoints | `GET /health` and `/health/live` do not touch the database. `GET /health/ready` performs a bounded `SELECT 1` and returns `503` when the database is unavailable, without exposing the database error. |
| Logging | Fastify logging redacts `Authorization`, `Cookie`, and `Set-Cookie`. Request bodies are not logged by default. Server logs may still contain internal Prisma error detail and should not be exposed publicly. |
| Rate limiting | The global limiter and login brute-force throttle are process-local. They work for a single long-lived process; they are not shared across multiple workers. The login throttle is now wired into `POST /api/v1/auth/login`. |
| Proxy trust | `TRUST_PROXY=false` by default. Enable it only if the hosting reverse proxy overwrites `X-Forwarded-For`; otherwise clients could spoof IPs and defeat per-IP limits. |

> **Node 20 dependency warning:** `npm ci` on Node 20.20.2 emits an
> `EBADENGINE` warning for `cookie@2.0.1`, a transitive dependency of
> `fastify → light-my-request`. `light-my-request` is Fastify's test-injection
> helper and is loaded lazily; it is not part of normal HTTP request handling.
> The full API suite, including `app.inject`, passes on Node 20.20.2. If the host
> offers Node 22, prefer it to remove this unsupported-engine warning; if only
> Node 20 is available, treat this as a residual upstream risk to verify in
> staging, not as proof of failure.

## 3. cPanel capabilities that must be confirmed

Check these in the actual cPanel account, or ask the provider. Do not infer them
from the existence of a Node.js icon.

| Capability | Why it matters | If absent |
| --- | --- | --- |
| Node.js **20+** (Node 22 preferred if available) | Fastify 5 and the project's ES2022/top-level-await code require it. `engines` now declares `>=20`; the transitive `cookie@2` warning makes Node 22 the cleaner choice. | Blocker. Do not downgrade Fastify or rewrite the runtime just to fit Node 18. |
| Node.js application runner | The API is a persistent server, not a static site or PHP script. It must stay running and receive HTTP requests. | Blocker unless the provider offers another supported long-lived Node process. |
| Passenger or equivalent | cPanel's Node.js Selector is commonly Passenger-based, but the actual runner and its startup-file rules must be confirmed. | Confirm the exact startup command, document root, and restart procedure before deploying. |
| Assigned `PORT` | Passenger-style runners usually assign a TCP port through `PORT`. The API already prefers `PORT`. | If the runner passes a socket path or an incompatible value, the startup strategy must be adapted and tested. |
| PostgreSQL server | Prisma is configured for PostgreSQL, not MySQL/MariaDB. | Blocker for this architecture. A managed PostgreSQL service is the alternative, but it requires TLS, network access, and explicit approval before changing the database host. |
| PostgreSQL version | Prisma 5+ requires at least PostgreSQL 9.6; 14+ is the operational recommendation. The host's exact version must be confirmed. | If the host only offers an unsupported/old version, use a supported managed PostgreSQL service. |
| Database network path | The app must reach PostgreSQL over localhost or a permitted private/public network. Remote access may require allowlisting and TLS. | Blocker until connectivity and TLS are proven. |
| SSH/terminal or equivalent | Prisma Client generation and production migrations normally need a shell command in the application root. | The app can be prebuilt on Linux elsewhere, but migrations and restore checks still need an approved execution path. |
| Outbound network during install | `npm ci` must fetch packages and the Prisma engine from the npm registry. | Prebuild a Linux artifact in a controlled environment, or ask the provider to allow the registry. |
| SSL for `api.exoexpress.ma` | The dashboard calls the API over HTTPS. Mixed content and bearer-token exposure are unacceptable. | Blocker until AutoSSL or another valid certificate is active. |
| DNS/application URL | The API hostname must resolve to the cPanel application and be routed to it. Current probes return `404`, not JSON. | If DNS does not point at this account, a DNS change is required and must be explicitly approved. |
| Backup/restore access | A verified database backup and a tested restore are required before migrations. cPanel's file backup may not include PostgreSQL. | Blocker for any schema-changing deployment. |
| Disk/quota | A full `npm ci` can be large (the local install is roughly 390 MB before pruning). Prisma also needs its native engine. | Check the quota before uploading or installing. |
| Worker/process count | The rate limiters are process-local. Multiple workers multiply limits and make them inconsistent. | For a single-worker deployment this is acceptable; for multiple workers, use a shared limiter and review the design first. |

## 4. Recommended cPanel application settings

These are target values, contingent on the actual cPanel interface:

| Setting | Recommended value | Notes |
| --- | --- | --- |
| Node.js version | `22` if offered, otherwise `20` | Do not select Node 18. Verify the runtime actually reports Node 20+. Node 20 is tested but emits the `cookie@2` engine warning described above. |
| Application root | A directory **outside** `public_html`, for example `~/apps/exo-api` | Never put the API inside `public_html` or replace the public website. |
| Application URL | `api.exoexpress.ma` | The URL and SSL setup are production changes and are not part of this audit. |
| Application startup file | `dist/server.js` | It must exist after `npm run build`. |
| Document root | Not applicable to a Node app; cPanel maps the application URL to the Node process | Do not point a document root at `public_html` for the API. |
| Environment | `NODE_ENV=production` | Required for production CORS checks and HSTS. |
| App mode | Production/long-running | Not a serverless/static function. |

If the cPanel interface does not allow a startup file outside the document root,
or does not support a persistent Node process, stop and treat it as a blocker.

### Port and bind test

Start the app once with the runner, then check the process logs. If it fails to
bind:

- Confirm the runner supplied `PORT` and that `API_PORT` is **not** set.
- If the runner requires a loopback listener, set `HOST=127.0.0.1` and restart.
- Do not publish the Node port directly to the internet. Traffic should reach
  the app through cPanel's web server/Passenger mapping.

## 5. Build and start on the host

Only after the cPanel capabilities above are confirmed and deployment is
approved, upload the **source/configuration files** for `apps/api` (not
`node_modules`, `dist`, or `.env`) to the application root:

```text
apps/api/
  package.json
  package-lock.json
  tsconfig.json            (self-contained; no workspace root required)
  src/
  prisma/
  scripts/                 (optional, needed for user:create)
```

`apps/api/tsconfig.json` now carries the compiler settings directly, so the API
directory builds without the monorepo root. Verify with `npm run build`; do not
assume the path.

Then, from the application root:

```bash
# NODE_ENV may already be production in cPanel. Force dev dependencies for the
# build even if the UI exported NODE_ENV=production.
npm ci --include=dev

# Generate the Linux Prisma Client. This must run on the server (or in a Linux
# build environment), not by copying the Windows node_modules.
npx prisma generate

# Compile TypeScript to dist/.
npm run build

# Confirm the expected entrypoint exists.
test -f dist/server.js

# If an initial staff account is required, create it before pruning dev deps.
# Use arguments appropriate to the role; never put the password in shell history
# or committed files.
# npm run user:create -- --email ... --name ... --role SUPER_ADMIN

# If a schema migration is approved, run it before pruning dev deps. It requires
# the verified backup described in section 7.
# npx prisma migrate deploy

# Remove build-only dependencies after generation/build/provisioning.
npm prune --omit=dev

# Confirm the generated client survived the prune and is a Linux build.
ls node_modules/.prisma/client
```

After `npm prune --omit=dev`, the Prisma CLI and `tsx` are gone. A later
migration or staff-account provisioning needs a temporary
`npm ci --include=dev` (or a separate release step); do not leave build tools
installed permanently just for this.

Start with the cPanel runner, or verify the exact command locally on the host:

```bash
npm start
# equivalent to: node dist/server.js
```

Do **not** run `npm start` against a Windows-generated `dist`/`node_modules`
directory. The Prisma engine would be the wrong binary and the API would fail
at the first database query.

### If the host has no terminal

Build on Linux (WSL, a Linux container, or a CI runner) using the same
`package-lock.json`, run `npm ci --include=dev`, `npx prisma generate`, and
`npm run build`. Then upload the Linux `dist`, generated Prisma Client, and
production dependencies as a release archive. Verify that `node_modules/.prisma/client`
contains a Linux `libquery_engine-*.so.node` file, not `query_engine-windows.dll.node`.
This path is not verified in the current environment and must be tested on a
staging copy before production.

## 6. Environment variables

Set these in the cPanel Node.js application environment, not in a committed
file and not in the dashboard bundle:

| Variable | Required | Placeholder / value |
| --- | --- | --- |
| `NODE_ENV` | Yes | `production` |
| `DATABASE_URL` | Yes | `postgresql://USER:PASSWORD@HOST:5432/DATABASE?schema=public` |
| `CORS_ORIGINS` | Yes in production | `https://www.exoexpress.ma` (exact origin; no trailing slash) |
| `TRUST_PROXY` | No | `false` unless the cPanel proxy overwrites `X-Forwarded-For` |
| `PORT` | Supplied by runner | Do not override it on cPanel |
| `API_PORT` | No | Leave unset on cPanel; it takes precedence over `PORT` |
| `HOST` | No | Default `0.0.0.0`; set `127.0.0.1` only if the runner requires it |
| `SESSION_TTL_DAYS` | No | `7` |
| `LOG_LEVEL` | No | `info` |
| `RATE_LIMIT_ENABLED` | No | `true` |
| `RATE_LIMIT_WINDOW_MS` | No | `60000` |
| `RATE_LIMIT_MAX` | No | `600` |
| `LOGIN_RATE_LIMIT_WINDOW_MS` | No | `900000` |
| `LOGIN_RATE_LIMIT_IP_MAX` | No | `40` |
| `LOGIN_RATE_LIMIT_ACCOUNT_MAX` | No | `8` |
| `MAX_ACTIVE_SHIPMENTS_PER_COURIER` | No | `30` |

Rules:

- `DATABASE_URL` is a secret. Do not paste it into tickets, chat, logs, or
  screenshots. URL-encode special characters in the password. For a remote
  database, use the provider's required TLS parameter (for example
  `sslmode=require`) and verify it with a real connection.
- `CORS_ORIGINS` must contain exact origins. `https://www.exoexpress.ma` and
  `https://exoexpress.ma` are different origins; add the second only if that
  hostname actually serves the dashboard. A trailing slash or path is rejected
  in production. `NODE_ENV=production` rejects an empty list, a wildcard, a
  non-HTTPS origin, or a non-origin URL.
- `NEXT_PUBLIC_API_URL` belongs to the **dashboard build**, not this API
  process. It is not a secret.
- Redis variables are not required by the current API.
- Never upload `.env` from a workstation. If the host requires a file, restrict
  its permissions and keep it outside the web root.

## 7. PostgreSQL: compatibility, backup, and migration

### Required database

- Provider: PostgreSQL (not MySQL/MariaDB).
- Prisma: `6.19.3` from the lockfile.
- Minimum: Prisma 5+ supports PostgreSQL 9.6 and newer; use a current supported
  release. **Recommendation: PostgreSQL 14+.** Confirm the host's actual version
  rather than assuming it.
- Extensions: none are required by the schema or migrations.
- IDs: generated by Prisma; no `pgcrypto`/`uuid-ossp` requirement was found.
- Encoding/timezone: use UTF-8 and a consistent timezone; verify the dashboard's
  date displays after deployment.

### Backup before any migration

Never assume an existing production database is empty. Before a schema change:

1. Confirm the database/user, migration history, row counts, and current
   `prisma migrate status` on a staging/read-only basis.
2. Take a provider snapshot **and** a logical backup if `pg_dump` is available.
3. Restore the backup into a **separate** database and verify row counts and
   `prisma migrate status` there.
4. Only then schedule the production migration with explicit approval.

Example commands (placeholders only; use a protected credential store and do not
paste real URLs into shell history):

```bash
pg_dump --format=custom --no-owner --no-privileges \
  --file=exo-before-YYYYMMDD.dump "$DATABASE_URL"

# Restore into a NEW, separate database, never over production:
pg_restore --no-owner --no-privileges \
  --dbname="$RESTORE_DATABASE_URL" exo-before-YYYYMMDD.dump
```

If cPanel does not provide `pg_dump`/`pg_restore`, use the provider's database
backup and restore facility. A cPanel "Home directory" backup alone does not
prove the PostgreSQL database is recoverable.

### Forward migration

After the backup is verified and approval is recorded:

```bash
# Run from apps/api with the production DATABASE_URL and the Prisma CLI
# still installed. This applies committed migrations only.
npx prisma migrate deploy
```

Do not run:

- `prisma migrate dev`
- `prisma db push`
- `prisma migrate reset`
- `prisma:seed`
- any destructive data cleanup

against production. The current startup code does not run any of these
automatically.

### Empty, newly provisioned database

1. Create a dedicated database and least-privilege application user in cPanel or
   with the database provider.
2. Set `DATABASE_URL` and confirm a TLS connection if the database is remote.
3. Take a baseline backup (empty database) and record it.
4. With explicit approval, run `npx prisma migrate deploy` from `apps/api`.
5. Create the first staff account with `npm run user:create` while dev
   dependencies are still installed. Do not use the seed script for production.
6. Create reference zones and tariffs through the authenticated admin API/UI or
   a reviewed, non-destructive data procedure. Do not run `prisma:seed` against
   production.

If the host cannot provide PostgreSQL, stop and evaluate a managed PostgreSQL
service. That changes the database host and possibly the network/TLS setup, so
it requires a separate decision and approval; do not silently switch providers.

## 8. Health, CORS, and login verification

Run these only after the app is started and before declaring success.

```bash
# Liveness: process is up, no database dependency.
curl -i https://api.exoexpress.ma/health

# Readiness: 200 only when PostgreSQL is reachable; 503 otherwise.
curl -i https://api.exoexpress.ma/health/ready

# CORS preflight for the dashboard origin.
curl -i -X OPTIONS https://api.exoexpress.ma/api/v1/auth/login \
  -H "Origin: https://www.exoexpress.ma" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"
```

Expected:

- `/health` → `200` JSON with `status: "ok"` and no secrets.
- `/health/ready` → `200` JSON with `checks.database: "up"`; `503` means the
  database connection or credentials are wrong.
- Preflight → `2xx` and `access-control-allow-origin: https://www.exoexpress.ma`.
  A missing header usually means `CORS_ORIGINS` is not exact, `NODE_ENV` is not
  `production`, or the app was not restarted.
- HTTPS response includes HSTS when `NODE_ENV=production`.
- Logs do not contain bearer tokens, cookies, database URLs, or passwords.

Then test a real login with a non-destructive staff account. Do not claim login
works based only on `/health`. Do not deliberately exhaust the login throttle on
production; test lockout behavior on staging.

## 9. Rollback

1. Keep the previous application release directory/archive and the previous
   environment values.
2. Stop the Node application.
3. Restore the previous code release and restart.
4. Restore the database only if the failed deployment changed data and the
   backup has been verified. Migrations are forward-only; there is no automatic
   `migrate down` in this project. Do not improvise a destructive rollback.
5. Re-run `/health` and `/health/ready`, then verify the dashboard still loads.
6. Record what changed and preserve the failed release and logs for diagnosis,
   without copying secrets into the report.

The static dashboard has its own rollback procedure in `DEPLOY_CPANEL.md`; it is
independent of the API.

## 11. Blockers preventing safe deployment

1. **Node.js 20+ is not confirmed** in the cPanel account. Node 18 is not
   compatible with the current Fastify 5 runtime. Node 20 passes the suite but
   emits an upstream `cookie@2` engine warning; Node 22 is preferred if offered.
2. **PostgreSQL is not confirmed.** Many cPanel plans provide MySQL/MariaDB
   only. Without a supported PostgreSQL database and network path, this API
   cannot deploy unchanged.
3. **The Node application runner is not confirmed.** A persistent process and a
   valid startup-file/PORT model are required; static hosting is not enough.
4. **Prisma generation and migration execution are not confirmed.** The host
   must allow `npm ci`, `prisma generate`, and `prisma migrate deploy` (or an
   approved Linux-built artifact plus a migration path).
5. **API DNS/SSL/reverse proxy is not confirmed.** `api.exoexpress.ma` currently
   returns `404`, not API JSON; the DNS target may not be this cPanel account.
6. **Database backup/restore is not verified.** No migration is safe until a
   restore has been tested on a separate database.
7. **No deployment approval or cPanel access has been provided.** No production
   migration, upload, DNS change, SSL change, or environment change has been
   performed.
8. **The dashboard is not uploaded** at `https://www.exoexpress.ma/dashboard/`
   (separate blocker; see `DEPLOY_CPANEL.md`).
9. **Multiple worker processes are unverified.** If cPanel starts more than one
   Node worker, the in-memory rate limits are per worker; this needs a design
   review before horizontal scaling.
